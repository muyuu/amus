# 音声メモ設計指針

## 概要

ゲーム中の発話を録音・書き起こし、ターンごとのメモとして蓄積する機能の設計を示す。

## 全体構造

録音と書き起こしの2層で構成する。録音は常時走り続け、その上にターン区間が乗る。

```
[常時録音リングバッファ]  ゲームが開始されている間ずっと回り続ける
        │
        └─→ 書き起こし  VADで発話を切り出し、逐次Whisperへ
                 ├─ トリガーワードを含むセグメント → ターン境界を開閉する
                 └─ それ以外 → 位置を含むターンのメモにする
```

ターン境界の検出は書き起こし結果のテキストから行い、専用の検知層は持たない。セグメントは
録音上の絶対位置を持つため、書き起こしが遅れて返ってもターンの位置は正確に定まる。

## 常時録音

`VoiceRecorder` は固定長リングバッファとして音声を保持する。

- 形式: 16kHz / mono / i16
- 容量: 上限に達したら古い側から上書きする
- ゲームが開始されている間は回り続ける

録音はユーザーの操作対象ではない。ターンの区間を切り出すための土台であり、開始・停止は
ゲームの有無に追従する。UI に出すのはターンの開始・終了だけで、録音状態は表示しない。

バッファは**絶対サンプル位置**（録音開始からの累計サンプル数）で参照する。リングバッファ
上の物理位置ではないため、上書きによって位置が変化しない。上書き済みの位置を要求された
場合は、実際に返せる先頭位置を添えて残っている分だけを返す。

ターンのタイムスタンプ、発話区間、検知位置はすべてこの絶対サンプル位置から導出する。

## ターン

ターンは録音上の時間区間 `[start_sample, end_sample)` として表現する。録音の開始・停止とは
独立しており、1回の録音の中に複数のターンが並ぶ。

境界はホットワードまたは手動操作で確定する。

- 開始ワード検知時、前のターンが開いたままならその位置で閉じてから新しいターンを開く
- 最大ターン長を超えた場合は強制的に区切る
- 直前の区切りを取り消す操作を提供する

終了ワードは任意である。ターンは連続するため、開始ワードだけでも区間は途切れず確定する。

## ホットワード検知

書き起こしたセグメントのテキストにトリガーワードが含まれるかを判定する。

照合はチャンク全体の結合テキストに対して行う。セグメントは句読点で区切られるため、
ワードがセグメントをまたいで割れることがある。

境界はワードの直後に置き、前の発話は閉じるターンへ、後ろの発話は開いたターンへ入れる。
ワード自体はメモにしない。

書き起こしはターンが開く前から走らせるため、ターンの先頭に来る発話も欠落しない。

誤検知への対処:

- 検知後のクールダウン中は同一ワードを無視する
- ターンが開いている間は開始ワードを無視する

トリガーワードは設定で変更できる。既定は「ターン開始」「ターン終了」。
設定時に以下を検証する。

- 4モーラ以上であること
- 開始ワードと終了ワードが音として十分に離れていること
- プレイヤー名・部屋名と衝突しないこと

設定画面には、実際に発声して検知されるかを確認するテスト機能を置く。

## 書き起こし

録音中の音声をVADで発話単位に切り出し、逐次バックグラウンドスレッドへ送る。ターン終了を
待たずに処理することで、会議フェーズに入った時点でメモが揃っている状態を保つ。

ターンの内外を問わず送る。ターン境界は書き起こし結果から決まるため、ターンが開く前の発話も
書き起こしておく必要がある。

Whisper が返すセグメントは無音の切れ目で決まるため、続けて喋ると数秒分が1つにまとまり、
どの発話がいつだったのかが失われる。メモは「いつ何を言ったか」を残すものなので、
トークンごとの時刻を求めさせ、句読点で区切り直してその時刻を持たせる。

結果のセグメントは録音上の絶対位置を持ち、その位置を含むターンのメモになる。どのターンにも
属さない位置のセグメントは捨てる。所属を送信時点ではなく位置で決めるため、ターンが後から
開いても、その区間の発話は正しくそのターンに入る。

セグメントの粒度はチャンクの大きさとは独立している。チャンクを大きくしても、メモの粒度と
タイムスタンプの細かさは保たれる。

タスクフェーズの発話は短いキーワード中心であり、1チャンクあたりの処理量は小さい。

### 実行バックエンドとモデル

処理時間の大半は、音声長によらず常に30秒分を処理するエンコードが占める。CPU ではこの
固定費がモデルの大きさを頭打ちにするため、GPU が使えるかどうかで使うモデルを変える。

| バックエンド | モデル |
|---|---|
| CPU | small |
| GPU | medium |

whisper.cpp のバックエンドはビルド時に固定される。1つのバイナリで全ての GPU を自動判別
することはできないため、Cargo feature で選ぶ。Windows / Linux は `gpu-vulkan`、macOS は
`gpu-metal`。Vulkan は NVIDIA / AMD / Intel を1つのビルドで賄え、実行側にはドライバ同梱の
ローダー以外を要求しない。

構成はビルドで決まり、実行時の設定では変えられない。GPU を使わせたい環境には GPU バックエンド
を含むビルドを、使わせたくない環境には含まないビルドを渡す。同じ選択を実行時にも持たせると、
モデルの取り直しを伴う設定が増えるだけで、バイナリの選択以上のものは得られない。

ビルドに GPU バックエンドが含まれていない場合と、含まれていても初期化に失敗した場合は
CPU + small で動く。構成どおりに動いているときは何も表示しない。GPU を含むビルドが CPU へ
退避したときだけ、その旨を画面に出す。GPU 版が遅いときの唯一の説明になるため。

バックエンドを変えても認識精度は変わらない。精度に効くのはモデルの大きさだけで、GPU はより
大きいモデルを現実的な処理時間に収めるための手段。

## 認識精度

### プロンプトのトークン予算

Whisper の `initial_prompt` は **224トークン**（`n_text_ctx` / 2）が上限で、超過分は
**先頭から切り捨てられる**。プロンプトはこの予算内に収める。

構築は優先度の低いものから並べ、重要な語ほど末尾に置く。

```
部屋名  →  ゲーム用語  →  プレイヤー名
（溢れたら切られる）        （必ず残る）
```

- トークン数は `WhisperContext::tokenize()` で実測し、予算を超える分は優先度の低い側から落とす
- ラベルや説明文は置かず、単語の羅列とする。プロンプトは直前の書き起こしの続きとして
  解釈されるため、説明文はトークンを消費するだけで効果がない
- 部屋名は代表表記のみを載せる。別名・英語表記は語彙補正側で扱う

### 語彙補正

プロンプトは出力を保証しないため、書き起こし結果を既知語彙で補正する。

```
Whisper出力  →  読みに正規化  →  既知語彙と照合  →  正規表記へ置換
```

既知語彙はプレイヤー名・部屋名・ゲーム用語で構成する。プロンプトと違いトークン予算が
無いため、優先度で削らず全てを対象にする。予算に収まらずプロンプトに載せられなかった語も
補正できる。

置換は読みが完全に一致する箇所に限る。誤って書き換えると発話そのものが失われるため、
取りこぼしより誤爆を避ける。重なる語があれば長い方を採る。

**漢字表記の語は、かなで認識された結果からは補正できない。** 読みを求める手段が無いため、
「きんこ」から「金庫」へは寄せられない。かな・カタカナ表記の語（部屋名の多くとプレイヤー名）
が対象になる。漢字表記の語を救うには、語ごとに想定する読みを持たせる必要がある。

この「読み正規化」はホットワード検知と共有する。トリガーワードの表記ゆれを同じ仕組みで
吸収する。ホットワード側は語が限られていて誤爆の影響も小さいため、こちらは誤りを許した
近似マッチを行う。

## 設定項目

| 項目 | 内容 |
|---|---|
| トリガーワード | 開始・終了ワード。検証とテスト機能付き |
| 最大ターン長 | 超過時に強制的に区切る |
| リングバッファ容量 | 保持する録音の長さ |
